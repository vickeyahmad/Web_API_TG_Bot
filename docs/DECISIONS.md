# Architecture Decisions

1. ASP.NET Core 10 is the main backend.
2. PostgreSQL is the central database.
3. Next.js will provide the customer website.
4. Start with a modular monolith.
5. All sales channels share the same backend.
6. Vendor integrations use separate adapters.
7. Start with manual payment and fulfillment.
8. Never expose vendor costs or credentials.
9. GitHub is the source of truth for project code.
10. Products have their own internal SKU (`InternalSku`) decoupled from external vendor product IDs.
11. Vendor mappings (`VendorProduct`) allow multiple suppliers per internal product with individual costs and priority rankings.
12. Multi-currency readiness: Customer selling currency (`PKR` default) and supplier costs (`PKR`, `USD`, `USDT`) are stored separately with explicit `decimal(18,4)` precision. No direct subtraction across differing currencies.
13. Public API outputs use strict DTOs (`CategoryDto`, `ProductSummaryDto`, `ProductDetailDto`) to ensure vendor details and vendor costs are never serialized, avoiding data leakage.
14. Future customer wallet ledger and payment provider requirements are planned without schema conflicts.
15. Central identity architecture: Single ASP.NET Core Identity store on `AppDbContext` using `ApplicationUser` and `ApplicationRole`. Serves administrators now and will support customers in future milestones without creating separate authentication backends.
16. Secure session management: HTTP-only authentication cookies (`.WebAPI.Admin.Auth`) configured with `SameSite = Lax` and sliding expiration. `SameSite = Lax` enables cross-subdomain requests (`admin.gogaabyte.com` to `api.gogaabyte.com`) with credentials while preventing cross-site attacks. Web API overrides default redirect behaviors to return 401 Unauthorized and 403 Forbidden.
17. Defense-in-depth against credential attacks: Built-in fixed window rate limiting on `/api/admin/auth/login` coupled with Identity account lockout (15-minute lockout after 5 consecutive failed attempts).
18. Controlled administrator provisioning: Initial administrator account is seeded on startup only if none exists and credentials are supplied through secure environment variables (`ADMIN_SEED_EMAIL`, `ADMIN_SEED_PASSWORD`) or `dotnet user-secrets`. No public registration or setup endpoints exist.
19. Preserved Security Stamp Validation & Instant Role/Active Checks: `OnValidatePrincipal` explicitly invokes `SecurityStampValidator.ValidatePrincipalAsync(context)` alongside checks for `user.IsActive` and admin role membership. With `SecurityStampValidatorOptions.ValidationInterval = TimeSpan.Zero`, password resets, demotions, and account deactivations revoke active sessions immediately on the next request.
20. Cross-subdomain CSRF token delivery: `GET /api/admin/auth/csrf` returns the CSRF request token in a non-cacheable JSON response (`Cache-Control: no-store, no-cache, must-revalidate`) while keeping the companion `.WebAPI.Antiforgery` cookie `HttpOnly = true`. This avoids assuming frontend JS can read host-only backend cookies across subdomains (`admin.gogaabyte.com` vs `api.gogaabyte.com`).
21. Centralized CSRF enforcement: Globally registered `AutoValidateAntiforgeryTokenAttribute` via `AddControllersWithViews` in `Program.cs`. All state-changing endpoints (`POST`, `PUT`, `PATCH`, `DELETE`) across all current and future controllers automatically require valid antiforgery tokens unless explicitly exempted with `[IgnoreAntiforgeryToken]`.
22. Admin Catalog Management & SKU Immutability: Dedicated `AdminCategoriesController` and `AdminProductsController` powered by `IAdminCatalogService`. To ensure referential stability and protect downstream orders/vendor mappings, product `InternalSku` is strictly immutable after creation.
23. Non-Destructive Catalog Lifecycle: Permanent deletion of categories and products is disallowed. Inactive states are toggled via dedicated `PATCH .../status` endpoints. Disabling a category automatically hides all its products from public customer-facing APIs without deleting records.
24. Admin Vendor Management & Multi-Currency Costs: Dedicated `AdminVendorsController` and `AdminVendorProductsController` powered by `IAdminVendorService`. Suppliers and costs remain completely decoupled from customer selling prices, and multi-currency supplier costs (PKR, USD, USDT) are preserved with decimal(18,4) precision without premature automatic conversions.
25. Relational Integrity & Non-Destructive Vendor Mappings: Vendor-to-product mappings enforce unique composite constraint `(VendorId, ProductId)` and foreign key referential integrity at both the application and PostgreSQL database level. Soft status toggling of vendors leaves existing mappings intact, and permanent deletion of vendor records is prohibited.
26. Centralized Order System & Immutable Historical Price Snapshots: All sales channels (Website, Telegram bot, future SMM panel, and Admin) share a single central order database and numbering format (`ORD-YYYYMMDD-XXXXXX`). Line items record immutable snapshots (`ProductSkuSnapshot`, `ProductNameSnapshot`, `UnitPriceSnapshot`, `TotalPrice`) at the time of order creation. Future price, name, or SKU updates to catalog products never alter past order records or financial statements.
27. Controlled Order Lifecycle Transitions, Permanent Audit History & Non-Destructive Referentials: Order state changes are strictly regulated via `OrderStatusTransitions` (11 defined states), prohibiting skipping steps (e.g. `PendingPayment` directly to `Completed`) and guarding terminal states (`Cancelled`, `Refunded`). Every transition is permanently logged in `OrderStatusHistory`. Destructive cascading deletes are prohibited on `Orders -> OrderItems` and `Orders -> OrderStatusHistory` using `DeleteBehavior.Restrict` in EF Core and `ON DELETE RESTRICT` in PostgreSQL, preventing accidental or programmatic deletion of orders containing financial items or audit logs. Referential integrity also enforces `Restrict` on customer and product deletion to guarantee complete financial ledger and audit trail preservation.
28. Dual-Scheme Session Architecture & Strict Admin/Customer Role Segregation: Administrator sessions (`.WebAPI.Admin.Auth`) and Customer sessions (`.WebAPI.Customer.Auth`) run on completely independent cookie authentication schemes (`Identity.Application` and `CustomerCookie`). Customers cannot access `/api/admin/*` endpoints, and client-supplied role claims during registration are completely ignored with server-side enforcement of `AppRoles.Customer`. Both cookie schemes enforce immediate active status checking and built-in security stamp validation on every request.
29. Customer Registration Security & Transactional Email Preparation: Customer self-registration enforces normalized email indexing, duplicate account conflict rejection (409 Conflict), ASP.NET Core Identity password complexity requirements, and brute-force protection via account lockout and rate limiting (`CustomerAuthLimiter`). Transactional email infrastructure is decoupled from authentication foundation: accounts are created initially with `EmailConfirmed = false`, architecturally prepared for email verification and password recovery in a dedicated future milestone without schema conflicts.
30. Durable Idempotency & Database-Enforced Customer Order Uniqueness: To prevent double-ordering from repeated client requests, network retries, or double clicks, customer order creation enforces an idempotency key passed via the `X-Idempotency-Key` header or request body. The key is persisted on the `Orders` entity with a PostgreSQL filtered unique index `IX_Orders_CustomerId_IdempotencyKey` scoped to each customer (`WHERE "IdempotencyKey" IS NOT NULL`). If a duplicate request arrives with identical order parameters, the existing order is safely returned (201 Created). If the same key is re-used with differing order parameters, it is rejected with `409 Conflict`. Concurrent duplicate submissions racing into the database are caught at the engine level via PostgreSQL unique violation code `23505`, rolling back the race-loser transaction and returning the winning order.
31. Server-Side Pricing, Snapshotting & Strict Customer Order Isolation: For all customer orders, pricing is resolved directly from live PostgreSQL database records (`Product.SellingPrice`), never from client payloads. `CustomerId` is extracted exclusively from the authenticated session (`ClaimsPrincipal`), and `SalesChannel` is assigned server-side. Inactive products or products in disabled categories are strictly rejected. Once placed, line item price snapshots remain permanently immutable against future catalog price adjustments. Customer order retrieval endpoints (`GET /api/customer/orders` and `GET /api/customer/orders/{orderNumber}`) enforce strict scoping by customer ID; requests attempting to view another customer's order return `404 Not Found` (never `403 Forbidden`), completely preventing order enumeration and cross-customer data leakage. All supplier details (vendor IDs, supplier costs, vendor notes) remain 100% excluded from customer DTOs.
32. Decoupled Central Payment Foundation & Immutable Transaction Snapshots: All sales channels share a single centralized payment database and numbering format (`PAY-yyyyMMdd-XXXXXX`). Payment records (`Payments`) are linked to orders via `OrderId` with non-destructive referential integrity (`DeleteBehavior.Restrict`), allowing multiple payment attempts per order (e.g., re-attempts after payment expiration or failure). Monetary amounts are stored with explicit high-precision `decimal(18,4)` and explicit currency codes (`PKR` default), preventing float rounding errors and currency mismatches. Durable idempotency is enforced via PostgreSQL filtered unique index `IX_Payments_OrderId_IdempotencyKey`.
33. Payment Status Lifecycle & Zero-Trust Verification Policy: Payment state transitions are strictly governed by `PaymentStatusTransitions` with defined states (`Pending`, `Paid`, `Failed`, `Expired`, `Refunded`, `PartiallyRefunded`). Terminal states (`Failed`, `Expired`, `Refunded`) are permanently locked. Under our zero-trust verification policy, untrusted client-supplied provider transaction references or raw gateway tokens never mark a payment as `Paid`. Creating a `Pending` payment never prematurely advances `OrderStatus`, preventing unauthorized fulfillment before verified settlement.
34. Permanent Payment Audit Trail & Multi-Currency Separation: Every payment state change requires an immutable log entry in `PaymentStatusHistory` capturing `PreviousStatus`, `NewStatus`, `Reason`, `ChangedByUserId`, and `ChangedAt`. Destructive cascading deletes on `Payment -> PaymentStatusHistory` are prohibited (`DeleteBehavior.Restrict`), ensuring an indelible financial audit trail. Multi-currency readiness enforces separate currency tagging for customer payments (`PKR`, `USD`, `USDT`), prohibiting premature automatic currency conversions or cross-currency mathematical operations.
35. Central Customer PKR Wallet & Strict Per-Currency Uniqueness: All sales channels (AI Tools Website, Digital Products Store, Telegram Bot, and SMM Panel) share a single central customer wallet system on `AppDbContext` linked to `ApplicationUser` (`CustomerId`). Each customer has at most one wallet per currency, enforced by unique composite index `IX_Wallets_CustomerId_Currency` in PostgreSQL. Initial balance starts at 0.0000 PKR, with non-negative balance enforced at the database engine level via `CK_Wallets_Balance_NonNegative` (`"Balance" >= 0`). Direct client-driven balance modifications are prohibited; all balance changes are mediated exclusively through internal `IWalletService`.
36. Append-Only Transaction Ledger & Non-Destructive Financial Retention: Every wallet balance mutation produces exactly one immutable ledger record in `WalletTransactions` recording `BalanceBefore`, `BalanceAfter`, `Amount` (> 0), `TransactionType` (Credit/Debit), `OperationKey`, `SourceType`, `SourceReferenceId`, and timestamps. Historical records are never modified or purged; corrections must be issued as traceable compensating entries. Referential integrity enforces `DeleteBehavior.Restrict` on both `User -> Wallets` and `Wallet -> WalletTransactions` (`ON DELETE RESTRICT`), preventing accidental or programmatic deletion of financial records. Note: Application-level append-only rules do not inherently protect against direct privileged database modifications; production environments should layer separate database-level role restrictions and audit logging.
37. Pessimistic Row Locking (`SELECT ... FOR UPDATE`), Atomic Commit & Durable Idempotency: To prevent concurrency race conditions, lost updates, and double-spending across concurrent requests or cluster instances, `WalletService` executes mutations inside an explicit database transaction with pessimistic row-level locking via PostgreSQL `SELECT * FROM "Wallets" WHERE "Id" = @id FOR UPDATE`. Prior to checking available debit balance, durable idempotency is verified against `WalletTransactions` (`IX_WalletTransactions_WalletId_OperationKey`). Replaying an identical operation safely returns the original transaction and resulting balance without re-mutating the balance; re-using a key with conflicting transaction details is rejected with 409 Conflict. If any part of the mutation fails, the transaction rolls back completely, ensuring balance and ledger state remain strictly atomic.
38. Manual PKR Wallet Top-Ups & Atomic Administrator Verification: Customers initiate manual wallet top-up requests creating central `Payment` records in `Pending` status with `Purpose = PaymentPurpose.WalletTopUp`, linked directly to customer PKR `Wallet` (`WalletId`). Customers submit manual transfer proof (bank TID/reference, transfer date, sender details) without crediting the wallet balance. Wallet crediting is restricted to independent administrator verification via `POST /api/admin/payments/manual/{paymentNumber}/approve`, which executes inside a single atomic PostgreSQL transaction with row-level locking (`SELECT ... FOR UPDATE`), updating the payment to `Paid`, recording verified bank transaction ID (`ProviderTransactionId`), logging `PaymentStatusHistory`, and crediting the PKR wallet via `IWalletService.CreditAsync` using stable operation key `WALLET_TOPUP:{PaymentId}`. Mutual exclusivity between order purchases and wallet top-ups is enforced at the database level by check constraint `CK_Payments_Purpose_Target`. The manual top-up feature is governed by a server-side configuration master toggle (`WalletTopUpOptions.Enabled = false` by default) for production safety, protecting both customer creation and administrator approval paths.
39. Multi-Account Bank Reference Scoping & Strict Financial Validation: To prevent double-crediting while avoiding false collisions across independent receiving channels (e.g., JazzCash vs Meezan Bank vs EasyPaisa), external transaction reference uniqueness is scoped to `(VerifiedReceivingAccount, ProviderTransactionId)` using partial unique index `IX_Payments_Paid_Account_ProviderTransactionId` (`WHERE "Status" = 'Paid' AND "VerifiedReceivingAccount" IS NOT NULL AND "ProviderTransactionId" IS NOT NULL`). Administrator approval strictly mandates: (a) explicit boolean confirmation that funds were verified in the receiving bank statement, (b) verified receiving account title/number, (c) verified transaction reference of at least 4 non-repetitive characters, rejecting ambiguous placeholders ("0000", "N/A", "CASH", "TEST"), and (d) exact match between verified amount/currency (PKR) and the requested payment amount. Mismatched amounts or missing confirmations are rejected without crediting wallets or altering payment state.
40. Customer Wallet Order Purchases, Invariant Lock Ordering, and Database Partial Unique Paid Guard: Authenticated customers can pay for pending orders directly using available PKR wallet balances via `POST /api/customer/orders/{orderNumber}/pay-with-wallet`. The operation coordinates between Orders, Payments, and Wallets within a single atomic PostgreSQL transaction. To eliminate deadlocks under high concurrency, pessimistic row locks are acquired in a strict, invariant global order: Order first (`SELECT ... FROM "Orders" WHERE "OrderNumber" = @p FOR UPDATE`), then Wallet second inside `IWalletService.DebitAsync` (`SELECT ... FROM "Wallets" WHERE "Id" = @id FOR UPDATE`). Double payment is prevented on three independent layers: (1) state transition validation (`PendingPayment` only), (2) durable debit idempotency using stable operation key `WALLET_ORDER:{order.Id}`, and (3) a database-level filtered unique index `IX_Payments_Paid_OrderId` (`WHERE "Status" = 'Paid' AND "OrderId" IS NOT NULL`) in PostgreSQL. If the customer wallet lacks sufficient balance, or if payment or status updates fail, the entire transaction rolls back cleanly with zero balance deduction and zero status change. The customer wallet purchase feature is guarded by a server-side configuration master toggle (`WalletPurchaseOptions.Enabled = false` by default) for production safety.
41. Administrator Order Management, Historical Snapshot Enforcement, and Controlled Paid to Processing State Progression: Dedicated `AdminOrdersController` powered by `IAdminOrderService` provides central order visibility and management across all future sales channels (AI Tools Website, Digital Products Store, Telegram Bot, SMM Panel). Role & permission enforcement is restricted strictly to `AppRoles.Admin` via cookie authentication (`.WebAPI.Admin.Auth`), antiforgery validation (`AutoValidateAntiforgeryToken`), and rate limiting (`AdminOrderLimiter`). `GET /api/admin/orders` supports structured querying across statuses, sales channels, customer identity (ID, email, name), order number, product SKU, and date ranges with bounded page sizes, ordered newest first. `GET /api/admin/orders/{orderNumber}` returns complete historical order snapshots, customer notes, full chronological `OrderStatusHistory` audit trail, and associated `OrderPurchase` payment attempts (excluding unrelated `WalletTopUp` payments). Starting fulfillment preparation is an explicit business action via `POST /api/admin/orders/{orderNumber}/start-processing` that enforces state machine rules (`Paid` to `Processing`), validates a verified `Paid` payment matching order amount and currency, appends an immutable `OrderStatusHistory` record, and executes under PostgreSQL pessimistic row-locking (`SELECT ... FOR UPDATE`) to prevent race conditions or duplicate history logs.
42. Central Fulfillment Foundation, Line-Item Isolation, and Unknown Vendor Outcome Fallback Safeguard: All sales channels (Website, Telegram bot, SMM panel, Admin) share a single central fulfillment foundation. Key architectural decisions: (a) Line-Item Isolation & Snapshots: Central `Fulfillment` entity is linked directly to `Order` and `OrderItem` (`DeleteBehavior.Restrict`). Each order item has at most one fulfillment record, enforced by PostgreSQL unique index `IX_Fulfillments_OrderItemId`. Original price snapshots, customer notes, and order lines remain permanently immutable. Partial fulfillments are supported within bounds (`0 <= QuantityFulfilled <= QuantityRequested`). (b) Fulfillment vs Order Status Decoupling: Line-item fulfillment status (`FulfillmentStatus`) is completely distinct from customer `OrderStatus` and `PaymentStatus`. A `Paid` or `Processing` customer order does not mean fulfillment has completed, and creating a fulfillment record never automatically completes an order. Status transitions are strictly governed by `FulfillmentStatusTransitions`. (c) Fulfillment Attempt Tracking (`FulfillmentAttempt`): Multiple vendor selections or manual delivery attempts are recorded chronologically per fulfillment, linked to `VendorProduct` mappings (nullable for manual delivery), with durable unique identifiers (`AttemptKey`). (d) Critical Unknown Vendor Outcome Safeguard: Network timeouts, gateway timeouts (504), socket disconnects, or unexpected supplier HTTP 500 errors produce an `Unknown` or `RequiresReconciliation` attempt status. Under our zero-trust supplier policy, network timeouts CANNOT be treated as confirmed vendor failures. Automatic fallback to secondary vendors is strictly prohibited (`FulfillmentAttemptRules.CanFallbackToNextVendor(status) == false`) until status reconciliation or human investigation verifies the order was not created, completely eliminating the risk of purchasing duplicate subscriptions across suppliers. (e) Strict Supplier Privacy & Financial Integrity: Fulfillment operations strictly forbid modifying customer wallet balances, transaction ledgers, or payment amounts. All vendor mappings, external product IDs, wholesale costs, and attempt records remain strictly internal and 100% invisible to customer-facing APIs.
43. Controlled Administrator Manual Fulfillment, Delivery Tracking & Multi-Item Order Completion: Dedicated administrator fulfillment workflow (`POST /api/admin/orders/{orderNumber}/items/{orderItemId}/manual-fulfillment/start`, `POST .../complete`, `GET .../fulfillments`) powered by `IFulfillmentService`. Key architectural decisions: (a) Pre-Condition Boundaries: Manual fulfillment requires that the customer order is strictly in `OrderStatus.Processing` with verified, matching `Paid` payment funds. Orders in `PendingPayment` or `Paid` (not yet transitioned to processing) are strictly rejected. (b) Duplicate-Delivery Prevention & Unknown Outcome Guard: Starting manual fulfillment requires that no active attempt is currently `Submitted`, and that NO previous vendor attempt on the line item ended in an unresolved `Unknown` or `RequiresReconciliation` status. Network timeouts are not proof of failure; manual fulfillment cannot be used to bypass unresolved external vendor orders, eliminating double-delivery or double-billing risks. (c) Tracked Manual Attempts & Zero Secret Storage: Manual attempts are recorded in `FulfillmentAttempt` with `VendorProductId = null` and initial status `Submitted`. Raw credentials, license keys, subscription passwords, or vouchers are strictly prohibited from storage in database entities, audit logs, or API payloads; only non-sensitive evidence metadata (e.g. support ticket references, delivery channel identifiers) is recorded. (d) Explicit Delivery Confirmation: Transition to `Completed` mandates administrator attestation (`ConfirmDelivered = true`), valid evidence references (sanitized against script injection), and non-sensitive delivery channels. Sets `QuantityFulfilled = QuantityRequested` and marks the manual attempt `Succeeded`. (e) Multi-Item Order Completion Invariant: Marking a line item fulfillment `Completed` only completes the parent `Order` if ALL purchased items for that order are fully fulfilled. If other line items remain in `NotStarted` or `InProgress`, the order stays in `Processing`. Order transition (`Processing` -> `Completed`) is logged in `OrderStatusHistory`. (f) Permanent Audit Trail (`FulfillmentStatusHistory`): Every fulfillment status transition is recorded in `FulfillmentStatusHistories` capturing `PreviousStatus`, `NewStatus`, `Reason`, `ChangedByUserId`, and `ChangedAt` with `DeleteBehavior.Restrict` on `Fulfillments` and `DeleteBehavior.SetNull` on `AspNetUsers`. (g) Invariant Lock Ordering & Concurrency Safety: Operations execute in explicit PostgreSQL transactions with pessimistic row locks acquired in invariant global order (Order first via `SELECT ... FOR UPDATE`, then Fulfillment). Simultaneous administrator completions or starts safely resolve with exactly one winner and one conflict/already completed response. (h) Production Feature Gate: Controlled via `ManualFulfillmentOptions.Enabled = false` by default, protecting both initiation and completion endpoints until manual operations are authorized.

44. Frontend Integration Readiness, Cross-Origin CORS Policies, Dual Cookie Schemas, and API Contract Standards: Preparation for future browser frontends (Customer Website at `tools.gogaabyte.com`, Admin Panel at `admin.gogaabyte.com`, and future SMM Panel at `smm.gogaabyte.com`) connecting to central backend (`api.gogaabyte.com`). Key architectural decisions: (a) Explicit Origin CORS Enforcement & Preflight Handling: Production origins are explicitly restricted to `https://admin.gogaabyte.com`, `https://tools.gogaabyte.com`, `https://smm.gogaabyte.com`, and `https://api.gogaabyte.com` with `AllowCredentials()`. Wildcards combined with credentials are strictly prohibited. Permitted request headers include `Content-Type`, `X-XSRF-TOKEN`, `X-Idempotency-Key`, `Authorization`, `Accept`, and `X-Requested-With`, guaranteeing browser preflight OPTIONS requests succeed for customer idempotent orders and payments. Development origins support `http://localhost:5173` (Vite / Lovable) and `http://localhost:3000` (Next.js). (b) Dual Isolated Cookie Authentication: Admin sessions (`.WebAPI.Admin.Auth`) and Customer sessions (`.WebAPI.Customer.Auth`) run on completely separate schemes with `HttpOnly = true`, `SameSite = Lax`, and sliding expiration. In production, `CookieSecurePolicy.Always` mandates HTTPS. Customer cookies cannot access admin routes; admin cookies cannot access customer routes without customer login. (c) JSON-Compatible 401/403 Responses: Override `OnRedirectToLogin` and `OnRedirectToAccessDenied` across all authentication cookie schemes to return uniform JSON envelopes (`ApiResponse<object>.Fail(...)`) instead of HTTP 302 redirects, ensuring client-side fetch handlers receive structured errors without HTML redirects. (d) Cross-Subdomain Non-Cacheable CSRF Delivery: State-changing requests (`POST`, `PUT`, `PATCH`, `DELETE`) require `X-XSRF-TOKEN` paired with the companion `HttpOnly` `.WebAPI.Antiforgery` cookie. Tokens are delivered via `GET /api/customer/auth/csrf` and `GET /api/admin/auth/csrf` with `Cache-Control: no-store, no-cache, must-revalidate`. Missing or invalid tokens return 400 Bad Request. (e) Zero Supplier Exposure in Customer DTOs: Strict DTO boundaries ensure supplier identities, external vendor SKUs, vendor purchase costs, and fulfillment attempts remain 100% internal and are never serialized to public customer APIs. (f) Centralized OpenAPI / Swagger Documentation: Enabled XML documentation generation to enrich development-only Swagger UI with request/response schemas, DTO descriptions, and endpoint annotations without introducing new dependencies.
